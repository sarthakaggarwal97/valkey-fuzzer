# Spec bridge

The spec bridge links a TLA+ model to real fuzzer runs. It does three things:
it model-checks the model's claims, turns a counterexample into ordinary
scenarios, and checks real runs against the model: the claims on the states a
run shows, for the bundles that have such a check
([What a PASS covers](#what-a-pass-covers)), and that the steps a run shows
are steps of the model ([The transition check](#the-transition-check)). It
does not prove that Valkey implements the model.

All three tools need Java 11 or later and `tla2tools.jar` (pass
`--tla2tools`, or set `TLA2TOOLS_JAR`; CI pins v1.7.4 with TLC 2.19),
except `conform` of a bundle that gives TLC nothing to evaluate (every
property `conform: excluded`, and no targets): it then runs without them,
and reports its [transition check](#the-transition-check) as not checked.
Nothing else needs them:
`pip install` brings no Java, and `run`, `validate` and `batch` work
without them, including the shipped experiments that name a bundle
(`spec: cluster-election`), since reading a bundle's mapping needs no TLC.
The one exception is a run of an approved bundle that needs TLC: its own
check cannot decide the run, so it is an `ERROR` ([In a run](#in-a-run)).
Without them a `spec` command exits `2` and
says what is missing and where to get the jar:

```text
$ valkey-fuzzer spec check cluster-election
Error: tla2tools.jar not found and java not found on PATH: the spec bridge needs Java 11 or later on PATH and tla2tools.jar (pass --tla2tools or set TLA2TOOLS_JAR). Get the jar CI pins with: curl -fsSL -o tla2tools.jar https://github.com/tlaplus/tlaplus/releases/download/v1.7.4/tla2tools.jar
```

Before anything runs, the jar is probed (`java -cp tla2tools.jar tlc2.TLC -h`)
for TLC's version and for `-dumpTrace`: a jar that does not run TLC, or runs
one older than 2.19 (the version the bridge is tested with), is an error,
exit `2`, naming the jar. The jar's SHA-256 is looked up among the releases
the bridge knows (`TLA_TOOLS_RELEASES` in `valkey_fuzzer/spec/tla.py`: v1.7.4,
the one CI pins, and v1.8.0, the first whose TLC dumps traces as JSON); another
jar runs with a warning on stderr, since its TLC may print what the bridge
reads differently, or is an error with `--strict`, which the model-check
workflows pass. `spec check` prints what it ran with (`Tools: TLC 2.19 from
tla2tools.jar (v1.7.4, sha256 ...)`) and records it in the report's `tools`:
`jar`, `sha256`, `release` (null for an unknown jar), `tlc_version`,
`json_trace`, and any `warnings`.

Each tool writes a JSON report with `--output`, and each takes `--timeout SECONDS`
(default 3600, one hour): once the command has run that long, SANY or TLC is
killed with its whole process group and that run fails. Reports and translated scenarios name the
bundle by its protocol, its files by their paths inside the bundle, and the
jar by its file name, so the same bundle gives the same reports anywhere.
The exception is an error about where a bundle is (one that cannot be
found or read, or a protocol name that finds another copy): its message
names the paths involved. The code is in
`valkey_fuzzer/spec/`.

## What a PASS covers

`spec check` model-checks a model. It says nothing about Valkey unless a
property is also evaluated against live runs. Of the four bundles that ship,
`cluster-election` is, and so is `replication`'s `SameOffsetSameData`, from
the trace's samples of each node's replication ID, offset and `DEBUG DIGEST`
([Samples](#samples)). The rest (`replication`'s two claims over data sets as
sequences, `persistence`, `slot-migration`) are model only: `spec conform`
reports which steps their runs took (each has shipped experiments that
publish them, [Bundles](#bundles)) and the states their samples showed, and
the data oracles compare data, but no oracle evaluates their properties.
`approved` claims do not change that; they say a maintainer reviewed the
model, not that a live check exists. No shipped bundle is approved today:
`replication` was, under an assumption (`AdoptOnLoad`) Valkey does not meet,
and went back to draft when its `holds_when` was corrected to what Valkey
does.

## Bundles

A bundle describes one protocol:

```text
<protocol>/
  claims.yaml          properties, scope, assumptions, bounds, exclusions, approval
  model.tla            MODULE model
  *.cfg                expected-safe TLC configs
  mapping.yaml         model actions and variables <-> implementation evidence
  sample.log           lines Valkey logged, at least one per log pattern of mapping.yaml
  negative-controls/   <name>.cfg, plus <name>.tla for a mutated model
  experiments/         optional: data-only experiments the counterexamples run in
```

A bundle is named by a path to its directory, or by its protocol name (no
`/`). A name is looked up in each directory of `$VALKEY_FUZZER_SPEC_PATH`
(separated like `PATH`), then in the bundles that ship with valkey-fuzzer:
`formal/` of a checkout, which the wheel installs as the package
`valkey_fuzzer.formal`. A name never means a directory of the current one
(write `./<name>` for that), so a scenario reads the same bundle wherever it
runs. The same rule applies everywhere a bundle is named: the `spec` commands,
and the `spec:` field of an experiment's components. A component that reads
the mapping when it runs also records the mapping's SHA-256 in the plan
(`spec_sha256`), so an edited mapping changes the plan and its digest, and a
run whose mapping no longer matches its plan stops with `ERROR`. The bundles ship in the wheel because a
shipped experiment that names one (`spec: cluster-election`) must work in any
install; the search path is for bundles that live elsewhere, such as drafts
and fixtures. Name a bundle's directory after its protocol.

[`formal/cluster-election/`](../formal/cluster-election/README.md) is the
failover election; its experiment ships with the Valkey experiments.
[`formal/replication/`](../formal/replication/README.md) is primary-replica
replication (PSYNC, full and dual-channel sync, promotion, restarts); its
two claims over data sets as sequences are model only, and `conform` checks
`SameOffsetSameData` (two nodes on one replication ID at one offset hold the
same data set) on the trace's samples of each node's `INFO replication` and
`DEBUG DIGEST`. The replication experiments (`valkey.replication-chaos`,
`valkey.replication-full-resync`, `valkey.replication-partial-resync`)
publish the steps and record the samples with the `valkey.replication-steps`
fragment.
[`formal/slot-migration/`](../formal/slot-migration/README.md) is atomic
slot migration (`CLUSTER MIGRATESLOTS`: the snapshot, the pause, the grant,
the target's claim, and its replica); `conform` reports which steps a run
took and the job states its `CLUSTER GETSLOTMIGRATIONS` samples showed.
`valkey.slot-migration-spec` migrates a slot under writes and kills the
target at its claim.
[`formal/persistence/`](../formal/persistence/README.md) is the order in
which one server writes its AOF files, manifest and RDB file through a
rewrite, `CONFIG SET appendonly` and a kill; `conform` reports only which
steps a run took. `valkey.aof-durability` and `valkey.save-crash-points`
publish those steps with the `valkey.persistence-steps` fragment.
Every bundle has a `scenario` section, so `spec translate` writes scenarios
from each one's counterexamples; which fault each injects, and which it
leaves to the experiment, is in the table below.

| Bundle | Experiment | Fault the scenario injects | Left to the experiment (`unmapped`) |
| --- | --- | --- | --- |
| `cluster-election` | `valkey.cluster-election-durability` | `Crash`: `kill-voter` after `granted`, at `vote_occurrence` | |
| `replication` | `valkey.replication-full-resync` | none: no counterexample takes `Crash` | `Crash`, `Disconnect` (the experiment's own stall), `LoadFails` |
| `slot-migration` | `valkey.slot-migration-spec` | `CrashT`: `kill-target` after `claimed`, `kill_delay_s` later | `Cancel`, `DropLink`, `PauseExpires`, `LoseBus` |
| `persistence` | `valkey.save-crash-points` | none: every property is violated before any kill | `Crash` (the experiment's crash point, swept by `nth`), `RewriteFails` |
`tests/fixtures/spec/register/` is a toy register that brings its own
experiment and runs on Valkey (see
[Onboarding a protocol with data only](#onboarding-a-protocol-with-data-only)).

**`claims.yaml`** holds these fields:

- `protocol` and `summary`;
- `status`: `draft` or `approved`. An approved bundle also needs
  `approved_by`, the maintainer who approved it. Drafts written by an AI
  always stay `draft`;
- `scope`: the Valkey files and functions the claims cover;
- `properties`: each has a `name` (an invariant or property defined in the
  model), `kind` (`invariant` or `property`), `statement`, and `holds_when`
  (the constant values under which the property is claimed; a constant the
  mapping pins with `value` must be pinned to the claimed value, or no run
  could ever be checked as claimed). It also lists
  `negative_controls`, the controls that must violate it, and `conform`:
  `true` (invariants only), or `{excluded: <why>}` when observed states
  cannot decide the property;
- `targets`: named state predicates of the model that a counterexample
  reaches. `conform` counts the runs that reach each one;
- `assumptions`, `bounds` (the constants every safe config must use; a
  config in the bundle's `nightly/` directory may raise an integer bound,
  see [spec check](#spec-check)), and `exclusions` (what the model leaves
  out);
- `max_unobserved_steps` (default `1`): how many steps of the mapping's
  `unobservable` actions `conform`'s [transition check](#the-transition-check)
  allows between two records; and `transitions: {excluded: <why>}` when the
  mapping cannot support that check.

**`mapping.yaml`** is the only place the implementation patterns live.
Experiments, observers, and oracles read them from here. Because they all
do, one wrong pattern would blind them all at once: `spec check`'s
`log_patterns` gate matches every `log` pattern against the bundle's
**`sample.log`**, lines Valkey logged (one or more per pattern), and fails
on a pattern that matches none.

- `sample`: what the trace observer (`valkey.observer.trace`) reads from
  every node in each sampling round, for the `sample: true` evidence:
  `info` (INFO sections), `digest` (`DEBUG DIGEST`), `digest_keys` (`DEBUG
  DIGEST-VALUE` of each key), `cluster` (the node's view from `CLUSTER INFO`
  and `CLUSTER NODES`), `slot_migrations` (`CLUSTER GETSLOTMIGRATIONS`), and
  `nodes_conf` (the `vars` line of `nodes.conf`, read from the file); `on`
  lists the event globs after which a round runs (every event without it).
  See [Samples](#samples). A bundle declares what it needs and nothing more;
  a mapping with a `sample: true` evidence needs this section, and a sample
  field can read only what it records.
- `evidence.<name>`: one kind of evidence. Each entry is either a fuzzer
  `event` (a name or a glob, with an optional `where` payload filter) or a
  `sample: true` state sample (a trace observation record, with an optional
  `where` filter on its fields). `log` is the line pattern that is published
  as the event; `logged_by: server` (default `any`) says only the server
  process logs it, so the lines of a fork child (an RDB or AOF child, role
  `C` in the line's `pid:role` prefix) are skipped, and a line both log (`DB
  saved on disk`) is one event. `fields` lists the captured fields and their
  types: `int`, `str`, `bool` (a JSON boolean or the word `true` or `false`),
  `node` (a `str` that names a node), or `node_id` (a node ID, as the trace
  header's `nodes.<node>.node_id` records it), which resolves to a node
  through that header. A field can also have a `path` (dotted, into the
  payload or the observation: `info.master_repl_offset`), a `default`, and a
  `map` that replaces captured values with the model's names (`{master:
  primary}`, or forty zeros with the model's `0`); a value the map does not
  list stays. An event entry can name the experiment `component` that
  publishes it; only events from that component (their `source`) are then
  this evidence. `after: {evidence: <name>, match: {<its field>: $field}}`
  says the record follows a record of that evidence whose fields match:
  conform holds it until that record is applied, and a record whose match
  never appears is one it cannot apply. `after` may also `take: [<field>,
  ...]` fields from the latest such record, for a line that does not carry
  them (the election's `won` line names no epoch; the win is of the election
  its winner last `started`).
- `action`: the model action this evidence shows. `step` says which model
  steps produce it (`changes` or `unchanged`, a variable), which
  variables' changed key is the acting process (`process`), and whether one
  record stands for several steps of the action (`repeats: true`, a line that
  reports every write at once). `translate` uses `step`, and `conform`'s
  transition check holds the action to it.
- `updates`: how this evidence changes the observed state. Each update is
  one of `set`, `max`, `add`, `remove`, `clear`, or `incr` on a state
  variable, with an optional `key` and `value`. In those, `$field` is a
  captured field, and `$field@Set` is that node's model value in the process
  set `Set`.
- `unobservable`: the model actions that no evidence shows, each with the
  reason.
- `processes`: the model constants that are sets of nodes, their model-value
  `prefix`, and the `members` rules that say which nodes belong to each set:
  an `evidence` and its `field` that names the node, an optional `where`
  filter, and `require`, the fields that must be present and not empty.
- `state`: every model variable, either `over` some process sets with an
  `init` value, or `hidden: <TLA+ expression>` with a reason. The
  observed-state check evaluates the properties with a hidden variable at
  that expression; the transition check starts it there and lets the model
  move it.
- `constants`: every other model constant, as a literal `value`, as a
  per-node `config` that `equals` a value (read from the trace header), as a
  scenario `input` that `equals` a value (for an experiment that sets the
  configuration from that input), as the `max_of` some state variables, or
  as a `field` of the run's records of one evidence (`{field: {evidence:
  acked, name: quorum}}`, an `int` field: the largest value any such record
  carries, the quorum Valkey's ACK line logs), never below `at_least`. A
  constant can say `why` it has that form.
- `scenario`: what `translate` writes. It names the experiment, maps
  deployment fields and inputs to model constants (`count`, or `constant`
  with a `map`), and lists the `faults`: the model action, the evidence it
  follows (`after`), the experiment's fault `component` that injects it, the
  experiment input that sets the trigger occurrence (`occurrence_input`;
  without one the fault fires on the first occurrence), and `target:
  same-process`. `unmapped` lists the model's fault actions the scenario
  does not inject, each with the reason: no fault component does it (a
  cancel is a command), or no counterexample takes it (the persistence
  properties are violated before any kill). A scenario with no `faults`
  sets only the deployment and the inputs, and the experiment runs its own
  schedule; every counterexample then translates. It also lists the timing
  `variants`; `occurrence_shift` needs an `occurrence_input` on every fault.

**`experiments/`** holds data-only experiment documents, in the format of
[Scenarios and experiments](scenarios-and-experiments.md), composed only of
installed components. `spec translate` and `spec check` load them next to the
installed experiments; `validate` and `run` load them with
`--experiment-dir <bundle>/experiments`. Their components name the bundle by
protocol (`spec: <protocol>`), so the protocol name must find this bundle.

## spec check

```bash
valkey-fuzzer spec check cluster-election --tla2tools tla2tools.jar --output assurance.json
```

This command runs SANY, then TLC on every safe config and on every negative
control, and then compiles the scenarios the controls' counterexamples
translate into. It takes `--experiment-dir` like `run`.
A check fails (exit `1`) if any gate fails. It is an error (exit `2`), not
a failure, when the bundle does not exist, or when SANY or TLC never started
(a corrupt jar) or was cut short by `--timeout`: such a run says nothing
about the model. A failed gate outranks an error.

A bound TLC cannot check in a pull request's time lives in a second config:
`<bundle>/nightly/*.cfg`, which `spec check <bundle> --configs nightly`
checks instead of the bundle's own `*.cfg` (the negative controls and the
other gates run as always). Such a config may raise an integer bound of
`claims.yaml` (`MaxEpoch = 3` where the claim says `2`), never lower or
change one. The [TLA+ Model Check (nightly)](../.github/workflows/tla-model-check-nightly.yml)
workflow runs it daily on every bundle that has a `nightly/` directory.
The budget for the pull-request check is five minutes per TLC run and
fifteen for the whole job on CI's four-core runner; `cluster-election` keeps
`MaxEpoch = 2` with two crashes there (330,207 distinct states, 15 s on four
workers) and checks a third epoch nightly (33.7 million states, 17 minutes),
and `replication` checks a second crash nightly (10.2 million states under
dual channel, 3 minutes; on the runner, past five).

| Gate | Passes when |
| --- | --- |
| `bundle` | `claims.yaml` and `mapping.yaml` parse and agree with the model text. |
| `log_patterns` | Every `log` pattern of `mapping.yaml` matches at least one line of the bundle's `sample.log`. The observers that publish the lines, the oracles, and `conform` all read their patterns from the mapping, so a pattern Valkey never logs would blind them all without a line to match. A mapping with no log pattern passes with a note. |
| `parsed` | Every module extends or instantiates only the standard modules (`Bags`, `FiniteSets`, `Integers`, `Naturals`, `RealTime`, `Reals`, `Sequences`, `TLC`) and the bundle's own, and SANY accepts `model.tla` and every mutated control module. |
| `claims_checked` | Every property is checked by a safe config whose constants meet its `holds_when`, and every bound equals the safe configs' value (a `--configs` config may raise an integer bound). |
| `model_checked` | TLC finds no error in any safe config. |
| `negative_controls` | Each control's TLC run reports its named property as violated. A control that passes means the claim cannot fail as configured (vacuous). |
| `experiment` | Each control's counterexample translates into scenarios of the mapped experiment that compile, and each mapped fault is a fault component of the compiled plan. A counterexample without a mapped fault action is listed as `no-fault`; at least one control must translate. A bundle with its own `experiments/` must be the bundle its protocol name finds. A mapping without a `scenario` section passes with a note. |
| `mapping_complete` | Every action TLC explored is mapped to evidence or declared unobservable, and every mapped action exists. An `error` when TLC reported no coverage to compare with. |
| `model_coverage` | TLC reported coverage; an `error` when it printed none, which says nothing about the bundle. The report lists, per action, the distinct and generated states, and the actions that `never_fired` in a safe config. |
| `approved_claim` | `pass` for approved claims, and `skip` (printed as `[SKIP]`) for a draft; it records the approval status. With `--require-approved`, a draft fails. A `skip` does not fail the check. |

The assurance report (`kind: spec-assurance`) records the tools (the jar's
SHA-256 and release, TLC's version, whether it dumps JSON traces, and any
warning), the `configs` directory when one was given, the claims (status,
scope, properties, assumptions, bounds,
exclusions), the mapping's SHA-256, and one entry per gate. Each TLC entry
has its exit code, its violation, its state counts and depth, its trace
length and format (`json` or `text`), and the output tail when it fails. A run cut short by the time limit
is marked `timed_out`; it, or a run whose tool never started, gives its gate
the status `error`, the report gets an `error`, and the check stops at that
gate. The `scope` field states the
limit: this is evidence about the model within its bounds. The
[TLA+ Model Check](../.github/workflows/tla-model-check.yml) workflow runs
`spec check` on every bundle and uploads the reports.

## spec translate

```bash
valkey-fuzzer spec translate cluster-election --control vote-before-save --out scenarios/
valkey-fuzzer spec translate BUNDLE --trace tlc.out --config the.cfg --out scenarios/
```

The command takes TLC's counterexample, either by running a negative
control or from a saved TLC output: its text, or the file a TLC that can
(v1.8.0 and later) writes with `-dumpTrace json`. When the probed jar can,
every TLC run of the bridge asks for that dump and reads the trace from it;
otherwise, and when the dump cannot be read (an error the report shows), the
trace is read from the `State N: <Action ...>` blocks of the text. JSON keeps
less than the text: a model value and a string are both strings, a set and a
sequence both arrays, a function and a record both objects. The reader
(`read_json_trace`) gives the names the config declares as model values
(`Primaries = {p1, p2, p3}`) back their type, reads an object keyed only by
them or by integers as a function, and an array as a sequence in the order
TLC wrote it (TLC writes a set's elements in a fixed order, so equal sets read
equal); the translation of a counterexample is the same from either. The
pinned TLC 2.19 has no `-dumpTrace`, so CI reads the text.
It writes one direct scenario, up to `--variants` nearby
variants, and `translation.json`. Each scenario's header and
`translation.json` name the bundle by protocol and the config by its path in
the bundle. The bundle's own `experiments/` are loaded with the installed
experiments and `--experiment-dir`. For each fault step, the scenario
triggers the fault on the last occurrence of the mapped trigger evidence
before that step, counted among all of that evidence's steps; with
`same-process`, only occurrences by the fault's target count. The
translation lists the model steps between the trigger and the fault. The
real fault fires when the trigger is seen, so those steps must fit in that
gap. The variants explore the gap by shifting the occurrence and by setting
the timing inputs. Every scenario compiles before it is written, each mapped
fault's `component` must be a fault of the compiled plan, and variants that
compile to the same inputs are dropped. A counterexample that takes some of
the mapped fault actions but not all is refused: the experiment's other
fault components would still fire, so the scenario would not follow it.

### Searching the model

```bash
valkey-fuzzer spec translate cluster-election --reach VoteLostInCrash --mutate --out scenarios/
valkey-fuzzer spec translate BUNDLE --reach all --tlc-timeout 120 --max-scenarios 20 --out scenarios/
```

A negative control gives one counterexample, so one scenario family. With
`--reach` and `--mutate` the command searches the model for counterexamples
instead, and translates each distinct one the same way:

- `--reach TARGET` (repeatable; `all` for every target of `claims.yaml`)
  runs TLC on each safe config with the invariant `~TARGET` (a module
  `reach.tla` that extends the model with `NotTARGET == ~TARGET`, checked
  along with the config's own invariants, which a safe config never
  violates), so the counterexample is a shortest path that reaches the
  target, and translates that path: a scenario that drives the real system
  to the state the target names, under the safe config's constants. A target
  no safe config reaches is `unreachable`: the election's
  `VoteLostInCrash` needs best-effort saves, which no safe config has. A
  path that takes none of the mapped faults is `no-fault`, and one the
  mapping cannot express (its fault follows no mapped trigger) is
  `untranslatable`, with the reason.
- `--mutate` runs TLC on each safe config with each boolean constant flipped,
  one at a time, and then with each pair flipped when the single flips were
  cheap (every run finished, and together they took no longer than one run's
  budget). Each violation found is translated under the flipped constants (a
  flipped `SyncBeforeAck` maps to `appendonly: "no"` through the mapping's
  `scenario.inputs`); a mutation under which every check holds is reported as
  `held`. A flip that gives another safe config's constants is `skipped`: TLC
  found no error there already. TLC reports the shallowest violation, which
  may take none of the mapped fault actions (under best-effort saves the
  election's first violation is a vote sent before its save, four states, no
  crash): the experiment has nothing to inject for it, so it is set aside
  (`without_fault`) and the mutation runs again without that property, until
  a violation with a fault is found (`violated`), or none of the claimed
  properties is left to violate (`no-fault`).
- Traces are deduplicated by their action sequence: a path two configs or
  mutations both find is translated once, and the others point at it
  (`duplicate`, `same_as`). Two traces with different actions can still
  compile to the same inputs (the election's pair flip adds a `LearnEpoch`
  step the scenario cannot see); those are kept.
- Each TLC run of the search may take `--tlc-timeout` seconds (default 300,
  the limit a batch's `conform_tlc_timeout_s` gives TLC), within the
  command's `--timeout`; a run that runs out is `timed_out`, recorded, and the
  search goes on to the next. `--max-scenarios` (default 50) caps the
  scenarios written: the last translation gets the variants that fit, and the
  runs after it are `not-run`, with the reason.

`translation.json` is then a search report (`kind: spec-search`) rather than
one translation: `targets` (per target, per safe config: `reached`,
`unreachable`, `duplicate`, `no-fault`, `untranslatable`, `timed_out`,
`error`, or `not-run`, with the run's seconds, states, depth, the path's
actions, and the scenarios written), `mutations` (per safe config, per flip:
`violated` with the property, `held`, `no-fault`, `skipped`, `duplicate`,
`untranslatable`, `timed_out`, `error`, or `not-run`), the summary lists
`unreachable` and `held`, why the search `stopped` early, the `translations`
(each as the single-counterexample report, plus its `source`), and every
scenario id. Each scenario's header says what found it. The exit code is 2
when a TLC run failed or never started; a search that found nothing to
translate exits 0 with the report.

On the shipped bundles, `--reach all --mutate` takes 12 s on
`cluster-election` (15 scenarios from three counterexamples, each found in
about 2 s after a vote-before-save violation was set aside; the two deep
negative controls that give the same scenarios take 31 and 34 s each), 19 s
on `replication` (two scenarios; the two flips that hold each exhaust
565,000 states in 7 s), 15 s on `slot-migration` (three scenarios; five
flips violate only without a crash), and nothing on `persistence` (no
boolean constant, no target). Only `cluster-election` names a target, and
its `VoteLostInCrash` is unreachable under its safe config (4 s).

## spec conform

```bash
valkey-fuzzer spec conform cluster-election RUN_DIR... --group-by save_behavior,election --output conform.json
```

The command reads run folders, `report.json` files, directories of them, or
`trace.jsonl` files. When a run folder has a trace observer's
`components/*/trace.jsonl`, the command uses it; otherwise it uses the
report's events. In a directory every run folder (one with `plan.json` or
`report.json`) counts: a run killed before it wrote its report counts by its
trace, and a folder whose report cannot be read, or that left neither a
report nor a trace, is an error for that run, never left out. It replays each run's records through the mapping into
observed states. TLC then evaluates the `conform` properties and the
targets on every state, through `INSTANCE model WITH <var> <- Trace[k].<var>`,
so the definitions come from the model itself.

The result for each property is `holds` or `violated`, with the first
failing step. A property is `claimed` for a run only when the constants
derived from the run meet its `holds_when`. A violation outside the claim is
reported, but it does not fail the check. The live oracle of the same bundle
(`valkey.oracle.cluster-election-safety`) derives the same constants from
the nodes' settings and reports a finding of a claimed property the same
way, so the two agree on what a run under `best-effort` shows. A run with no mapped evidence is an
error, never a pass, and so is a run with a mapped record the mapping cannot
apply (a field missing or of the wrong type, a `node_id` the trace header
does not list), since the states that record would show are never checked.
A run that recorded a trace (its report's evidence names a `trace.jsonl`)
that is missing or unreadable is an error too: its events alone would miss
what the trace's samples carry.
An update keyed on a node outside the process set it ranges over (a sample of
a replica updating a primary's variable) is skipped with a note. The report also gives live action coverage (how many
runs observed each action, plus the unobservable actions), the targets
reached, and the `--group-by` tables. A run whose trace recorded a different
mapping digest gets a drift note.

The report says what this command checks: `observed-state check, transition
check, and action coverage`, and the `refinement` it amounts to
([What the transition check proves](#what-the-transition-check-proves)).
With `--no-transitions` it is the observed-state check alone, as before.

### The transition check

The same TLC run checks that the run's observed steps are steps of the model.
TLC starts from the first observed state, with every hidden variable at the
mapping's `hidden` value, and walks the records in order:

- A record with an `action` is a **step**: the model must take that action
  (any of its parameters: `\E p \in Primaries : HandleRequest(p)`), from the
  model's own `Next`, to a state that agrees with what the record says. Its
  `set`, `incr` and `clear` updates say the variable (at that key) now holds
  the observed value; `add` and `remove` say the set at that key holds, or
  lacks, the value; a `max` update is a lower bound a step cannot check. The
  mapping's `step` rule adds what the action `changes` or leaves `unchanged`
  (a denied vote leaves `lastVote`), and whether the record stands for
  several steps of its action (`repeats: true`: the register's one
  `writes.seeded` line is as many `Write` steps as it reports keys). A step
  whose updates changed nothing
  observed (a denied vote, a save) still counts: the action must be possible.
  A step may also take **no model step** when earlier steps already account
  for it (the stutter rule, as in `[Next]_vars`).
- Between two records the model may take up to `max_unobserved_steps`
  (`claims.yaml`, default `1`) steps of the actions the mapping lists as
  `unobservable`, and no other: the save of `nodes.conf` before the vote it
  lets leave, a candidate learning an epoch. An action a line would show
  must be shown by a line.
- A record without an `action` (a `sample`) is not a step: it **raises** the
  variables it reports to what it reports (`max`) or sets them (`set`), and
  the model goes on from there. The run began in a cluster with a history
  (the epochs its formation bumped), so the first samples calibrate the
  model's epochs; nodes.conf samples lag the file, so they only raise.

TLC explores every way the model can explain the records (which unobservable
steps, which parameters) and stops at the first path that explains them all.
The conform report (and a run's own `conform` section) gains, per run:

```json
"transitions": {"checked": 34, "max_unobserved_steps": 1, "holds": true, "tlc_states": 333}
```

`checked` counts the records after the first (steps and samples). When no
path explains every record, `holds` is `false` and `first_violation` gives
the first record no model step reaches (`index`, the record `to` with its
event and fields, and the record `from` before it): a `Win` logged before the
ACKs it needs, a vote ACKed by a candidate after the crash that should have
lost it. The run then `fail`s, under the same rule as a violated property: an
approved bundle's run `FAIL`s ([In a run](#in-a-run)), a draft's is reported. The bundle's
report counts the runs with a violation (`transitions.violated_in`). Without
TLC, the check is reported as `skipped` (a draft) or is an error (an approved
bundle, whose claims decide the run).

#### What the transition check proves

A pass is **observed-projection refinement**: for every record the mapping
applies, the model has a behavior that takes the same actions in the same
order and agrees, after each, with everything the record says. It is not full
refinement, and three things stay unchecked:

- **Hidden variables.** They start at the mapping's `hidden` value and the
  model moves them; the run never confirms them. A hidden variable the model
  reads in a guard (`bio` in `SaveConfig`) is the model's guess, so a step the
  model forbids only through hidden state is not caught, and a `hidden` value
  no initial model state has can make the first steps impossible.
- **What a record does not say.** A step constrains only the variables its
  updates touch (and its `step` rule); the model is free elsewhere. A step
  the model can take with some unlogged side effect is accepted.
- **The actions no line shows.** Up to `max_unobserved_steps` unobservable
  actions between two records are free: with the default `1`, a run may hide
  one unlogged save, learned epoch or client write between any two lines. A
  bundle whose log needs more raises the knob in `claims.yaml`; each step
  multiplies the branches TLC explores, so measure (`tlc_states` in the
  report; the election traces of 35 to 80 observed states take 300 to 7,000
  TLC states and one to three seconds).

The check is only as sharp as the mapping's observed state. `cluster-election`
observes most of its model, so a win without a quorum, a vote that leaves
before its save under `sync`, or an ACK of a vote that a crash lost is a
violation. The quorum is the model's `Quorum` constant, read from the
`quorum` the candidate's ACK lines log (a `field` constant of the mapping):
Valkey needs a majority of the slot-owning primaries, while the mapping's
`Primaries` holds every node that ever voted, so after a promotion a majority
of `Primaries` would ask for more votes than Valkey does and a second
election's win would have no model step. `persistence` observes only `crashes` and `slot-migration`
only `faults`, so their checks say little more than that the faults happened
when the model allows them. `replication` excludes the check
(`transitions: {excluded: ...}` in `claims.yaml`): its samples carry
replication IDs as hex and data sets as digests, which the model's steps
cannot compute (it numbers IDs from `nextId` and appends writes), and the
primary a replica follows stays hidden, so no model step relates two sampled
states; the check needs the model's own encodings and `primaryOf` from the
samples.

The check also needs the model's `Next` to apply its actions directly, as
every shipped model does (`\E p \in Primaries : HandleRequest(p) \/ Crash(p)`);
`conform` splits that text by the mapping into the actions a line shows and the
unobservable ones, and refuses a `Next` that takes steps through another
operator.

### Samples

An event is a step: it counts for its model action and applies its updates.
A sample is an observed state, not a step: the trace observer
([`valkey.observer.trace`](components.md#valkeyobservertrace)) read it from
the node, and its updates set the variables to what the node reported, so
variables the log lines never show (a node's replication ID, offset and data
set; a cluster node's epochs on disk; a slot migration job's state) become
observed instead of `hidden`. A sample changes the observed state only when
it differs from the last one, and it counts for no action. When a sample sets
a variable to another value than the events had it at, the sample is taken
(the node said so) and the disagreement is reported in the run's
`sample_mismatches`, by variable, key, inferred and sampled value, never
overwritten in silence; a sample that supersedes a sample is what samples do.
A `max` update from a sample only raises a variable, for a reading that lags
the truth (`nodes.conf` on disk).

What a round reads from each node is what the bundle's `mapping.yaml` asks
for in its `sample:` section, so an experiment that names the bundle
(`spec: <protocol>`) samples what the bundle needs and nothing more. The
rounds run on the observer's `interval_s` (0.25 s by default), after the
events the section's `on` globs name (every event without them), at the
start, and at the end. A node's INFO, digests and slot migrations are read
in one `MULTI`/`EXEC`, so one sample's offset and digest are of one instant;
a sample of two nodes is two instants, which is why a property that compares
two nodes' offsets (`ReplicaIsPrefix`) stays excluded, and one that compares
two nodes at equal IDs and offsets (`SameOffsetSameData`) does not.

| Bundle | `sample:` | Variables observed from samples |
| --- | --- | --- |
| `cluster-election` | `cluster`, `nodes_conf` | `currentEpoch` (raised by `CLUSTER INFO`), `diskEpoch`, `diskVote` (raised by the `vars` line of `nodes.conf`, read from the file, so a killed node's last save counts) |
| `replication` | `info: [replication]`, `digest` | `role`, `off`, `replid`, `replid2`, `secondOff`, `backlog` (`INFO replication`) and `data` (`DEBUG DIGEST`, standing for the data set); a replica is sampled while it streams, since in a full sync or a restart's load it reports its old ID over data being replaced |
| `slot-migration` | `cluster`, `slot_migrations` | `exp`, `imp`, `track` (the export, import and tracking jobs' states, mapped onto the model's) |
| `persistence` | none | none; its claims need the AOF directory and manifest |

A sample costs the node one `MULTI`/`EXEC` of two to four commands. INFO and
the cluster commands take well under a millisecond; `DEBUG DIGEST` hashes
every key and value, about 3 µs a key on an optimized build (30 ms at 10,000
keys, 270 ms at 90,000, measured on three nodes with one primary and two
replicas), and the node serves nothing while it runs. So the period is the
knob: the `valkey.replication-steps` fragment samples once a second
(`interval_s: 1.0`), which costs a node 0.4% of its time at the workloads'
default 1,200 keys and 1.5% at 5,000; at the observer's default 0.25 s the
same run would spend 1.4% and 6%. A data set of 100,000 keys would stall each
node a quarter of the time even at one second: sample `digest_keys` (`DEBUG
DIGEST-VALUE` of named keys, 0.1 ms for ten) instead of `digest` there. The
rounds run on their own thread, so a run's wall time does not grow with them:
the replication chaos example took 33.1 to 34.3 s over four runs with the
digest and 33.2 to 33.3 s over two without, inside the run-to-run noise.

### In a run

Every run whose plan names a bundle (a component whose config has `spec:
<protocol>`, as the election and replication experiments' observers do)
checks itself against it as its report is written, whichever command ran it
(`run`, `replay`, each `minimize` attempt, a batch's worker), once its trace
is complete: the same check as `spec conform BUNDLE RUN`, into the report's
`conform` section, by bundle. TLC comes from `$TLA2TOOLS_JAR` and `java` on
`PATH`, and runs for at most `conform_tlc_timeout_s` (a [batch
option](cli.md#batch), default 300 seconds, which a run outside a batch
uses): a check it stops is an error whose reason names the option. Each
bundle's entry has:

```json
"conform": {
  "cluster-election": {
    "approved": false,
    "status": "fail",
    "violated": ["OneWinnerPerEpoch"],
    "first_violated": {"claim": "OneWinnerPerEpoch", "state": 41, "step": {"state": 41, "why": "Win", "evidence": "won", "t": 1763.2, "fields": {"node": "valkey-4", "epoch": 9}}},
    "tlc_seconds": 1.8,
    "properties": {"OneWinnerPerEpoch": {"status": "violated", "claimed": true, "states": [41, 42], "first": {}, "previous": {}}},
    "transitions": {"checked": 38, "max_unobserved_steps": 1, "holds": true, "tlc_states": 412}
  }
}
```

`approved` says whether the bundle's claims decide the run; `status` is
`pass`, `fail`, `error`, `skipped` (a draft that needs TLC, without TLC),
`unexercised` (the run took no mapped step: its plan names the bundle, but
nothing it did shows the protocol, as a replication chaos wave that only
stalls a replica briefly; never a pass), or `not_run` (the run ended
`ERROR` or `SKIP_UNSUPPORTED`, before its verdict); `violated` lists the
claimed properties the observed states violated, and `transitions` when the
[transition check](#the-transition-check) found a step the model cannot
take; `first_violated` names the first of them, the observed `state` (its
index in the trace) that violates it, and that `step` as `spec conform`
reports it; `tlc_seconds` is TLC's time; and the rest is the full check
(`properties`, `transitions`, `states`, `actions`, `sample_mismatches`,
`notes`, `constants`, `error` or `reason`), as `spec conform` writes it per
run. A run whose plan names no bundle has `"conform": null`.

For a bundle whose claims are approved, the check is part of the run's
verdict: a claimed violation is the failed component `spec-conform:<bundle>`
of the outcome (its `summary` the violated claims, its `diagnostics` the
bundle, `violated` and `first_violated`), so the run `FAIL`s with that
component named in its summary (`spec conform cluster-election:
OneWinnerPerEpoch violated; ...`), `failed_components`, and failure signature,
and `minimize` keeps a reduction only while the same claims fail, `replay`
prints the result (`Spec conform cluster-election: fail: OneWinnerPerEpoch
violated`), and a [bug zoo](bug-zoo.md#caseyaml) case names the check in
`fail`. A draft's findings are recorded, never in the verdict.

| Conform result | Approved claims | Draft claims |
| --- | --- | --- |
| a claimed property violated, or a step the model cannot take (the transition check) | the run `FAIL`s | reported only |
| an error (no mapped evidence, a record it cannot apply, a trace the run recorded that is missing or unreadable, TLC failed or ran past `conform_tlc_timeout_s`, or no TLC for a bundle that needs it, or for its transition check) | the run is an `ERROR` (`spec-conform:<bundle>` is an errored component) | reported only (`skipped` without TLC; the transition check alone is reported as not checked) |
| a violation outside the claim, a pass | reported only | reported only |

Every entry says whether the bundle's claims are `approved`, and only an
explicit `approved: true` decides a run: an entry without the flag is read as
a draft's. A bundle that cannot be loaded counts as approved: the plan named
it, and nothing says its claims are a draft. A check that fails outright (an
exception in `spec conform`) still gives each bundle an entry with the
exception as its error, so the report says why rather than nothing. The
report is written before the check and again after it, so a run killed
during TLC leaves a report whose `conform` is `null`.

### In a batch

A [batch](cli.md#batch) takes each run's own `conform` section as it is:
its worker runs no second TLC, its verdict (status, summary, failure
signature with the failing component `spec-conform:<bundle>`) is the run's,
and the section is kept when a passing run's folder is pruned. A run from
before the section (an older report) is checked by its worker after the run,
into the run folder's `conform.json`, and judged by the batch under the same
table; such a run whose worker ended before it checked it (no
`conform.json`) is an `ERROR` for an approved bundle and reported only for a
draft. So a soak or a per-merge batch checks every run that exercises a
protocol, and an approved model is checked wherever its experiments run.

The batch's `summary.json` has a `conformance` entry per bundle, and
`conformance/<protocol>.json` holds the full report over the runs checked
(see [the batch folder](cli.md#the-batch-folder)); the entry lists the runs
with a step the model cannot take under `transition_violations`.

## Writing a bundle

To draft a bundle, by hand or with an AI, follow these steps:

1. Write `model.tla` (`MODULE model`) with named actions in `Next`, the
   invariants, and the target predicates.
2. Write one safe config, plus a negative control for every property: a
   config, or a mutated module, whose TLC run violates exactly that
   property. List only that property in the control's config. A mutated
   module changes actions, never the property: it must keep `model.tla`'s
   definition of the property, and of every operator the property uses, word
   for word, or take them with `EXTENDS model`. Otherwise a control could
   define the property as `FALSE` and pass while the model's own property
   is vacuous, so the bundle is rejected.
3. Write `claims.yaml` with `status: draft`.
4. Write `mapping.yaml`: map every variable and every constant, and every
   action to evidence or to `unobservable`. An experiment's
   `valkey.observer.log-trigger` rule without a `pattern` takes the mapping's
   pattern for its `publish` event (`spec: <protocol>`). Put one line Valkey
   logged for each `log` pattern in `sample.log`, taken from a real log or
   from the format string in the Valkey source.
5. If no installed experiment can inject the faults the mapping names, add
   one under `experiments/` (see below).
6. Run `valkey-fuzzer spec check` until every gate passes. Then run
   `spec translate --control` and `valkey-fuzzer validate` on the scenarios
   it writes.
7. A maintainer reviews the claims and the mapping, then sets
   `status: approved` and `approved_by`. Only then can
   `spec check --require-approved` be a required check.

## Onboarding a protocol with data only

A new protocol needs no fuzzer code: the bundle holds the model, the
mapping, and an experiment composed of installed components. The mapping
says which component realizes what: each fault names the fault `component`
that injects it, and each piece of evidence is an event that a component
publishes (optionally pinned with `component`), such as a
`valkey.observer.log-trigger` rule that publishes a log line with the
mapping's pattern. `spec check` compiles the experiment through the
counterexamples, so a bundle whose experiment cannot inject its faults fails
a gate before anything runs.

The register in `tests/fixtures/spec/register/` is the worked example. Its
model acknowledges writes, saves them, and may crash; the claim is that with
`SyncBeforeAck` an acknowledged write survives a crash, and the negative
control `ack-before-save` acknowledges before saving. Its experiment,
`experiments/toy.register.yaml`, runs that on one Valkey primary:

| Model | Experiment component | Evidence in `mapping.yaml` |
| --- | --- | --- |
| `Write`, `Ack` | `writes` (`valkey.workload.key-value`, preload only) | `writes.seeded`: Valkey acknowledged every write |
| `Crash` | `crash` (`valkey.fault.process-signal`, SIGKILL on `writes.seeded`, restart) | `crash.injected` |
| state after the crash | `reload` (`valkey.action.command` `DEBUG RELOAD`) and `reload-log` (`valkey.observer.log-trigger`, `spec: register`) | `register.loaded`, from `Done loading RDB, keys loaded: N` |
| `SyncBeforeAck` | input `appendonly` (`yes` with `appendfsync always`) | constant `{input: appendonly, equals: "yes"}` |
| the verdict | `data` (`valkey.oracle.ledger`) | every acknowledged write must survive |

End to end, from the repository root, with a `valkey-server` on `PATH`:

```bash
export VALKEY_FUZZER_SPEC_PATH=tests/fixtures/spec    # the register names itself: spec: register
EXPERIMENTS=tests/fixtures/spec/register/experiments
valkey-fuzzer spec check register --tla2tools tla2tools.jar --timeout 600
valkey-fuzzer spec translate register --control ack-before-save --tla2tools tla2tools.jar --out scenarios/
valkey-fuzzer validate scenarios/*.yaml --experiment-dir "$EXPERIMENTS"
valkey-fuzzer run scenarios/spec-register-ack-before-save.yaml --experiment-dir "$EXPERIMENTS" --artifact-dir runs/
valkey-fuzzer spec conform register runs/ --tla2tools tla2tools.jar
```

The translated scenario sets `appendonly: "no"`, so the run FAILs: the
crash loses the acknowledged writes, as the counterexample says it may.
`conform` reports `AckedDurable` violated outside the claim. The same
scenario with `appendonly: "yes"` PASSes, and `AckedDurable` holds within
the claim. `tests/test_live_spec_register.py` runs these steps.
