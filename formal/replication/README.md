# Primary-replica replication (TLA+)

A [spec bridge](../../docs/spec-bridge.md) bundle. `model.tla` models Valkey's replication between a primary and
its replicas (`src/replication.c`): PSYNC on two replication IDs, full sync over one channel or two (dual-channel
replication), the backlog, promotion and `REPLICAOF`, failed loads, and restarts from an RDB file. A node's data set
is the sequence of writes it applied and its offset is `primary_repl_offset`; a replication ID with an offset names
a data set, and PSYNC trusts that naming. The model checks that Valkey's rules keep it unique.

| Model action | Valkey code |
|---|---|
| `Write` | a client write; `feedReplicationBuffer` advances the offset only on a node with a backlog |
| `Stream` | a replica applying the stream |
| `Trim`, `FreeBacklog` | `incrementalTrimReplicationBacklog`; `replicationCron` freeing the backlog after `repl-backlog-ttl` under a new ID |
| `PartialSync` | `primaryTryPartialResynchronization` accepting (`+CONTINUE`), `replicaProcessPsyncReply` moving a changed ID to replid2 |
| `FullSync` | `+FULLRESYNC` to the end of the load; `syncCommand` gives a primary without a backlog a new ID first |
| `DualFork` | `+DUALCHANNELSYNC`, then the RDB channel's fork and `$ENDOFF` |
| `DualContinueEarly`, `DualLoadContinued` | the main channel's `+CONTINUE` before the load ends, then `dualChannelSyncSuccess` |
| `DualLoadFirst`, `DualContinueLate` | the load ends first (`replicaAfterLoadPrimaryRDB` with the RDB channel at `RDB_LOADED`), then `+CONTINUE` |
| `LoadFails` | a load that fails after the flush: `Discarding the half-loaded data` |
| `Disconnect` | the link drops; the replica caches its primary (`replicationCachePrimary`) |
| `Promote` | `replicationUnsetPrimary`, `shiftReplicationId` |
| `Follow` | `replicationSetPrimary`, `replicationCachePrimaryUsingMyself` for a primary |
| `Save` | `rdbPopulateSaveInfo`: the ID and offset only with a backlog (primary) or a primary, live or cached (replica) |
| `Crash` | a restart through `loadDataFromDisk`: a primary keeps the file's ID as replid2, a replica caches itself |

## Properties

- `OneHistoryPerId`: any two claims on one replication ID (a primary with a backlog, a replica streaming or holding a
  cached primary, a secondary ID with a backlog, an RDB file with replication info) name the same data set at every
  offset both reach.
- `ReplicaIsPrefix`: a streaming replica holds a prefix of its primary's history at the same offsets.
- `SameOffsetSameData`: two nodes that could continue the same replication ID and stand at the same offset hold the
  same data set. It is `OneHistoryPerId` at equal offsets, in the terms a run's samples show: each node's
  `master_replid`, `master_repl_offset` and `DEBUG DIGEST`.

## Checked against a live run

`spec conform` evaluates `SameOffsetSameData` on the states a run's trace samples show
([Samples](../../docs/spec-bridge.md#samples)): `valkey.observer.trace` reads `INFO replication` and `DEBUG DIGEST`
from every node in one transaction, and the mapping sets `role`, `off`, `replid`, `replid2`, `secondOff`, `backlog`
and `data` (the digest) from them. `OneHistoryPerId` and `ReplicaIsPrefix` compare data sets as sequences at
every offset (through `Gap`, the data set's length less the offset), which a digest cannot give, and a replica's
offset against its primary's at one instant, which two samples are not; both are model only, and the ledger and
data-consistency oracles compare data after a run. A `spec check` PASS says the model holds within its bounds, not
that Valkey does; the negative controls are the part that describes Valkey.

## Files

| File | Holds |
|---|---|
| `model.tla` | the model and the three properties |
| `model.cfg` | single-channel replication (the default), Valkey as it is: must find no error |
| `dual-channel.cfg` | dual-channel replication with the fix of fuzzer issue #133 (`AdoptOnLoad`): must find no error |
| `nightly/model.cfg`, `nightly/dual-channel.cfg` | the two above with a second crash: too slow for a pull request under dual channel, checked by the nightly workflow (`spec check replication --configs nightly`) |
| `negative-controls/keep_old_id_on_load.cfg` | Valkey as it is: must violate `OneHistoryPerId` (#133) |
| `negative-controls/keep_id_without_backlog.tla` | freeing the backlog keeps the ID: must violate `OneHistoryPerId` |
| `negative-controls/no_shift_on_promotion.tla` | a promoted replica keeps its ID: must violate `OneHistoryPerId` |
| `negative-controls/save_info_without_primary.tla` | an RDB file always records the ID: must violate `OneHistoryPerId` |
| `negative-controls/no_second_offset_check.tla` | PSYNC on replid2 ignores `second_replid_offset`: must violate `ReplicaIsPrefix` |
| `negative-controls/write_without_offset.tla` | a write does not advance the offset: must violate `SameOffsetSameData` |
| `claims.yaml` | the properties, scope, assumptions, bounds and exclusions (status `draft`) |
| `mapping.yaml` | the log lines that show each step, the samples (`sample:`) that show each node's IDs, offsets and digest, and the `scenario` `spec translate` writes |

Each `.tla` control `EXTENDS model` and replaces one action, so it checks the model's own property.

The claims hold for Valkey as it is over one channel: `holds_when` is `DualChannel = FALSE, AdoptOnLoad = FALSE`,
what `model.cfg` checks. A run's channel comes from the trace header (`dual-channel-replication-enabled`, which
the `replication-trace` observer records per node), so a dual-channel run is outside the claim: a violation there
is reported, not held against the run. Over two channels the claims hold only with the fix of #133
(`dual-channel.cfg`). The claims were approved on 2026-11-12 under `AdoptOnLoad = TRUE`, which Valkey does not do,
and went back to draft when that was corrected; `SameOffsetSameData` is new since, so a maintainer re-approves them
as they stand.

## Results (3 nodes, 2 writes, 5 replication IDs, 1 crash, 2 promotions or `REPLICAOF`s)

`valkey-fuzzer spec check replication` passes every gate in about three minutes on 12 cores: `model.cfg` has
564,909 distinct states and `dual-channel.cfg` 7,368,305, with no error; each control's counterexample is 3 to 10
states long (`write_without_offset` violates `SameOffsetSameData` at the third state: a full sync, then a write).

A second crash (`MaxCrashes = 2`) is where a bug that needs one node to crash twice, or two nodes to crash, lives.
It is checked nightly, not on every pull request: on four TLC workers `model.cfg` goes from 564,909 distinct
states (13 s) to 743,973 (16 s), but `dual-channel.cfg` from 7,368,305 (145 s; 297 s on CI's four-core runner)
to 10,186,888 (184 s here, past the five minutes a pull-request run may take on the runner), and the claims'
bounds hold for every safe config at once. `nightly/model.cfg` and `nightly/dual-channel.cfg` hold the raised
bound; the [TLA+ Model Check (nightly)](../../.github/workflows/tla-model-check-nightly.yml) workflow runs them.

`keep_old_id_on_load` is Valkey today, and it is a bug: when a dual-channel replica's snapshot finishes loading
before the main channel's `+CONTINUE`, `replicaAfterLoadPrimaryRDB` creates a backlog after the replica's old offset
but keeps its old ID and offset until `+CONTINUE`. Promoted in that window (or after the sync then fails), the
replica shifts its old ID onto the primary's data, and a former replica at that old ID and offset continues with 0
bytes and keeps its old data. TLC's counterexample has 10 states; it was reproduced on Valkey unstable and filed as fuzzer issue
[#133](https://github.com/sarthakaggarwal97/valkey-fuzzer/issues/133). The safe `dual-channel.cfg` checks the fix
that adopts the snapshot's ID and offset when the load ends.

The model does not show the replica exit of fuzzer issue #12: there `LoadFails` is what Valkey should do on a disk
load whose main channel closes, and Valkey exits instead.

## Scenarios

`spec translate replication --control <name>` writes scenarios of `valkey.replication-full-resync` on the model's
three nodes (one primary, two replicas). No counterexample takes `Crash`; the one fault a counterexample takes, the
link drop of `keep_old_id_on_load`, is what the experiment injects itself (`stall-replica`, a `SIGSTOP` the primary
answers by closing the link) on its own timer rather than on a mapped line, so the scenario injects no fault
(`unmapped` in `mapping.yaml`: `Crash`, `Disconnect`, `LoadFails`): it sets the deployment, and the variants sweep
the stall (`pause_s`). `DualChannel` sets no input, since the experiments take `dual-channel-replication-enabled`
from the deployment's `server_config`. Every control translates. Run on Valkey 9.1.3, the direct scenario showed
`Disconnect` and `FullSync` to `spec conform`.

## Checking runs

`spec conform replication RUN` replays a run's mapped log lines, crashes and samples, reports which steps it took,
and has TLC evaluate `SameOffsetSameData` on every observed state. The replication experiments
(`valkey.replication-chaos`, `valkey.replication-full-resync`, `valkey.replication-partial-resync`) publish the
lines and record the samples with the `valkey.replication-steps` fragment (`valkey.observer.log-trigger` and
`valkey.observer.trace`, `spec: replication`; the fragment also enables `DEBUG`), and a batch checks each of their
runs this way (see [In a batch](../../docs/spec-bridge.md#in-a-batch)). A crash is a SIGKILL fault or a kill of
the replication chaos action. A sample of a replica in a full sync is left out until its load ends: it still
reports its old ID and offset over data being replaced, and the model's `FullSync` is one step. The `link` comes
from the log lines only: INFO's `up` and `down` are coarser than the model's dual-channel states. A sample whose
`role` disagrees with the lines is reported in `sample_mismatches`. The other two properties are model only
(`conform: excluded` in `claims.yaml`); the ledger and data-consistency oracles compare data after a run. A run with
no mapped step is an error. The four dual-channel steps are unobservable as such: Valkey logs `+CONTINUE` and the
end of the load, and which step a line shows depends on their order.

## Run

Needs Java 11 or later and `tla2tools.jar`
([Java and the jar](../../docs/spec-bridge.md#java-and-the-jar) has the
download and its checksum).

```bash
valkey-fuzzer spec check replication --tla2tools tla2tools.jar --output assurance.json
valkey-fuzzer spec translate replication --control keep_old_id_on_load --tla2tools tla2tools.jar --out scenarios/
valkey-fuzzer run scenarios/spec-replication-keep_old_id_on_load.yaml --artifact-dir runs/
valkey-fuzzer spec conform replication runs/
```
