# Atomic slot migration (TLA+)

A [spec bridge](../../docs/spec-bridge.md) bundle. `model.tla` models Valkey's atomic slot migration
(`CLUSTER MIGRATESLOTS`, `src/cluster_migrateslots.c`) of one slot from a source primary S to a target primary T,
which has one replica R: the handshake, the forked snapshot with the slot's writes streamed behind it, the pause and
the failover grant, T's claim under a new config epoch, S learning the claim on the cluster bus, T's cleanup of a
failed import, and R following the import through T's replication stream and taking over when T crashes.

| Model action | Valkey code |
|---|---|
| `Write` | a client write to the node that takes writes to the slot; S feeds it to T from the fork on (`clusterFeedSlotExportJobs`) |
| `Start` | `CLUSTER MIGRATESLOTS` on S: connect and send `SYNCSLOTS ESTABLISH` |
| `TEstablish` | `clusterCommandSyncSlotsEstablish`: T hides the slot (`setSlotImportingStateInAllDbs`), propagates ESTABLISH, replies `+OK` |
| `SFork` | `slotMigrationJobReadEstablishResponse`, `slotExportJobBeginSnapshotToTargetSocket` |
| `TApply` | T applies the snapshot or a fed write and streams it to R; after `SNAPSHOT-EOF` it sends `REQUEST-PAUSE` |
| `SPause` | `slotExportTryDoPause`: pause client writes, send `PAUSED` |
| `TPaused` | `clusterCommandSyncSlotsPaused`: send `REQUEST-FAILOVER` |
| `SGrant` | `clusterCommandSyncSlotsRequestFailover`: send `FAILOVER-GRANTED` |
| `TClaim` | `clusterCommandSyncSlotsFailoverGranted`, then `performSlotImportJobFailover` and `finishSlotMigrationJob` |
| `TClose`, `TCleanup` | `clusterHandleSlotMigrationClientClose` on T; the deferred cleanup (`delKeysNotOwnedByMyself`) and FINISH |
| `RApply` | R applies ESTABLISH (a tracking job), the keys, the deletes and `SYNCSLOTS FINISH` |
| `Deliver`, `LoseBus` | a bus message read (`clusterUpdateSlotsConfigWith`, `clusterUpdateSlotExportsOnOwnershipChange`), or lost with its dead sender |
| `DropLink` | the migration connection drops; S stays paused after the grant |
| `Cancel` | `CLUSTER CANCELSLOTMIGRATIONS` on S |
| `PauseExpires` | the pause ends at its timeout (`isSlotExportPauseTimedOut`) |
| `CrashT`, `Promote` | T crashes; R wins the election (`clusterFailoverReplaceYourPrimary`, `clusterCleanSlotImportsOnPromotion`, `verifyClusterConfigWithData`) |

## Properties

- `OneWriter`: at most one node takes client writes to the slot.
- `NoAckedWriteLost`: every acknowledged write is held by a live node, or is on its way to R in T's stream.

Both hold only under three constants that are not Valkey as it is (`claims.yaml` lists them as assumptions):

- `CancelKeepsPause`: a cancel after S granted the failover keeps S paused until it learns the owner. Valkey
  unpauses (`finishSlotMigrationJob`), though `FAILOVER-GRANTED` has left; upstream's test "Export unpauses when
  cancelled" asserts the unpause, with T held by `DEBUG SLOTMIGRATION PREVENT-FAILOVER` so that it never claims.
  When T reads the grant and claims the slot before it reads the close, S and T both take writes until S learns the
  claim, and then S deletes the writes it took (negative control `cancel_unpauses`).
- `ExpiryAfterClaim = FALSE`: S's pause outlasts T's claim. Valkey's pause ends at its timeout and logs "Write loss
  risk!" (`pause_expires_after_claim`): a documented window.
- `ClaimReachesReplica`: R learns T's claim before T acts on it, as legacy `CLUSTER SETSLOT` replicates to the
  replicas first. Valkey sends the claim to R only on the bus, and `SYNCSLOTS FINISH` does not change R's view of
  the owner, so R promoted after T crashed without that message deletes the slot's keys
  (`replica_misses_claim`, a crash and a lost message). The voters refuse R, and send it an UPDATE with the claim,
  only when its request claims another slot of T whose config epoch the claim raised; T here owns no other slot.

## Checked against a live run

None of these properties is evaluated against a live run. `valkey.slot-migration-spec` migrates a slot under writes,
kills the target at its claim and publishes this bundle's steps (`spec: slot-migration`), so a batch reports which
steps each of its runs took, but nothing checks a property on a run. A `spec check` PASS says the model holds within
its bounds, not that Valkey does; the negative controls are the part that describes Valkey.

## Results (3 writes, 3 faults)

`valkey-fuzzer spec check slot-migration` passes every gate in about ten seconds on 12 cores: `model.cfg` has 8,236
distinct states and no error, every action fires, and each control's counterexample is 10 to 17 states long.

`cancel_unpauses` is a known bug: upstream PR valkey-io/valkey#5327 (open) reports it, with a reproduction, and
fixes it as `CancelKeepsPause` models, by leaving exports in `failover-granted` running. `replica_misses_claim` is
a bug reproduced on unstable d5763ea44 as the control's trace (sarthakaggarwal97/valkey-fuzzer#140): with T's bus
messages to R dropped, R applies `SYNCSLOTS FINISH`, T is killed, and R, elected with no slots, deletes the imported
keys, a write `WAIT` confirmed on R included. valkey-io/valkey#2724 (open) reports that the promoted replica does not
claim the slot, but not that it deletes the keys.

## Scenarios

`spec translate slot-migration --control replica_misses_claim` writes scenarios of `valkey.slot-migration-spec`:
three primaries with a replica each (S is shard 0's primary, T shard 1's, R its replica; the third primary gives R
the second vote its election needs), writes to the slot of `{s}` while `valkey.action.migrate-slots` moves it, and
`kill-target` (`valkey.fault.process-signal`) kills the node that logs the claim, `kill_delay_s` after it: the
model's `CrashT` after `TClaim`. The steps between them in the counterexample (a write to T, R applying T's stream)
must fit in that delay, which the variants sweep (0, 0.2 and 1 s). The other controls take no fault the scenario
injects: `Cancel` is a command, `PauseExpires` a timeout, `DropLink` and `LoseBus` would need a partition (root,
iptables), so `mapping.yaml` lists them as `unmapped` and `spec check` reports those controls as `no-fault`. Run on
Valkey 9.1.3 with `kill_delay_s` 1, the migration succeeded, T was killed, R was elected, every acknowledged write
survived, and `spec conform` saw `Start` through `TClaim`, `Deliver`, `RApply`, `CrashT` and `Promote`; with no
delay, S's pause ran to its timeout ("Write loss risk!", `PauseExpires`) since T died before S learned the claim.

`Cancel`, `DropLink` and `LoseBus` have real components in `valkey.slot-migration-chaos`
(`valkey.action.slot-migration-chaos`, [components](../../docs/components/actions.md#valkeyactionslot-migration-chaos)): its
waves kill the source or the target, cut the two apart, or cancel the migration at a phase read from `CLUSTER
GETSLOTMIGRATIONS` (`started`, `snapshot`, `handoff`, `finished`), heal, and check that the cluster converged and the
slot's keys survived. They stay `unmapped` for `spec translate` because a scenario injects every fault component of
its experiment's plan and no counterexample takes two of `CrashT`, `Cancel` and `DropLink`, so
`valkey.slot-migration-spec` carries `CrashT` alone. Both experiments publish the same lines, so `spec conform`
replays a chaos run as well: its kill of the target is `CrashT` (the `crash-wave` evidence, from the action's
`endpoint-killed` event), and a one-wave run's transitions hold; the model has one migration, so a run of several
waves is reported as a violation at its second. The `finished` evidence records how each endpoint's job ended
(`state`), and is the line a fault triggers on to land once a migration is over.

## Checking runs

`spec conform slot-migration RUN` replays a run's mapped log lines (published by `valkey.observer.log-trigger` with
`spec: slot-migration`) and the samples of `valkey.observer.trace` (the mapping's `sample:` section: each node's
cluster view and `CLUSTER GETSLOTMIGRATIONS`), reports which steps it took, and sets `exp`, `imp` and `track` from
the export, import and tracking jobs' states ([Samples](../../docs/spec-bridge.md#samples)).
`valkey.slot-migration-spec` publishes the lines, and a batch checks each of its runs this way (see
[In a batch](../../docs/spec-bridge.md#in-a-batch)). Both properties need each node's view of the owner and the
writes it holds, which a run does not show in the model's terms (the model names its nodes `S`, `T` and `R`; the
samples name run nodes), so conform checks neither (`conform: excluded`) and needs no TLC. `mapping.yaml` pins the
three constants to the claims' `holds_when` (the fixes, not Valkey as it is), so a run is checked as claimed once a
property can be: a run in which Valkey as it is lets two nodes write would fail, as it should.
